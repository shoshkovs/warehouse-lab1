# Отчёт по лабораторной работе № 1

## Тема и цель работы

**Тема:** классы, конструкторы, наследование, копирование и перемещение объектов на примере системы управления складом.

**Цель:** реализовать склад с полиморфными товарами, применить паттерны «Фабричный метод» и «Итератор», обеспечить глубокое копирование и перемещение склада, проверить работу программы в демонстрационных сценариях.

Программа написана на C++17. При подготовке отчёта 25 октября 2026 года выполнены сборка с предупреждениями `-Wall -Wextra -Wpedantic`, проверки AddressSanitizer/UndefinedBehaviorSanitizer и запуск демонстрации.

## 1. Постановка задачи

Согласно этапу 5 задания необходимо:

1. Создать склад, добавить товары через разные фабрики и вывести их через итератор.
2. Скопировать склад, изменить товары копии и проверить независимость оригинала.
3. Переместить склад через конструктор перемещения и проверить отсутствие копирования товаров.
4. Выполнить поиск по ID, категории и цене, удаление по ID и индексу.
5. Перенести товар между складами через `transferTo`, изменить его остаток и цену.
6. Проверить правило пяти, итератор, валидацию атрибутов и фабрики.
7. Подготовить UML-диаграмму, описания паттернов и правила пяти, результаты и выводы.

## 2. Структура программы

- `include/` — объявления классов в заголовочных файлах `.h` с `#pragma once`.
- `src/` — реализации классов, консольное меню `Console.cpp` и точка входа `main.cpp`.
- `tests/` — проверки классов и записей логирования.
- `CMakeLists.txt` — сборка библиотеки, демонстрации и тестовой программы.
- `docs/warehouse.puml` — исходник UML в формате PlantUML; `warehouse.mmd` и `warehouse.svg` — исходник Mermaid и готовое изображение.
- `docs/results/` — фактический вывод демонстрации и проверок.

`Warehouse` хранит `std::vector<std::unique_ptr<Product>>`: каждый умный указатель отвечает за один товар. Вместимость ограничивает число записей товаров, а не сумму их остатков `quantity`.

Общие поля `Product`: ID, название, цена, остаток, вес, категория и невладеющий указатель на текущий склад. ID может назначаться общим статическим счётчиком либо передаваться явно фабрике. Внутри одного склада повторные ID при добавлении запрещены.

`Price`, `Quantity` и `Weight` скрывают числовые значения и запрещают отрицательные числа через конструкторы и сеттеры. `Quantity::change` изменяет остаток на заданную величину. Цена и количество представлены `int`, вес — `double`.

## 4. Паттерн «Фабричный метод»

**Задача паттерна:** создавать конкретные товары через единый интерфейс, отделив выбор их типа от работы склада.

В [ProductFactory.h](../include/ProductFactory.h) объявлен абстрактный `ProductFactory` с виртуальным `createProduct`. Шесть фабрик переопределяют этот метод и создают соответствующие товары: `Smartphone`, `Laptop`, `TShirt`, `Jacket`, `Milk`, `Bread`.

Метод принимает ID, название, целую цену, количество и дробный вес. Реализации в [ProductFactory.cpp](../src/ProductFactory.cpp) создают проверяемые объекты атрибутов и возвращают `std::unique_ptr<Product>`. Фактический тип товара сохраняется, а вызывающий код работает через общий интерфейс.

Пример из демонстрации:

```cpp
SmartphoneFactory factory;
warehouse.addProduct(factory.createProduct(42, "Phone", 100, 2, 0.2));
```

Фабрика создаёт объект, а склад принимает владение. Сама фабрика товары не хранит.

`clone()` решает другую задачу: создаёт копию уже существующего конкретного товара и используется для глубокого копирования склада. Это механизм прототипа; наличие `clone()` не заменяет отдельную иерархию фабрик. Реализована разрешённая заданием альтернатива «Фабричный метод»; отдельная абстрактная фабрика семейств товаров не добавлялась.

## 5. Паттерн «Итератор»

**Задача паттерна:** последовательно обходить товары, не открывая внешнему коду контейнер склада.

[WarehouseIterator](../include/WarehouseIterator.h) оборачивает стандартный итератор вектора и предоставляет:

- `operator*` — доступ к текущему товару как `Product&`;
- префиксный `operator++` — переход к следующей позиции;
- `operator==` и `operator!=` — сравнение позиций.

`begin()` возвращает начальную позицию, `end()` — позицию после последнего элемента. Разыменование `end()` недопустимо. Внутри `operator*` выражение `**current_` сначала получает `unique_ptr` из вектора, затем сам товар из умного указателя.

[ConstWarehouseIterator](../include/ConstWarehouseIterator.h) возвращает `const Product&`. Через этот результат можно читать описание и атрибуты, но нельзя вызывать изменяющие методы товара. Константные версии `begin()` и `end()` выбираются для `const Warehouse`.

```cpp
WarehouseIterator iterator = warehouse.begin();
while (iterator != warehouse.end()) {
    std::cout << (*iterator).getInfo() << '\n';
    ++iterator;
}
```

Это собственный простой итератор для требуемого обхода, а не полная реализация всех требований STL ForwardIterator. Структурные изменения вектора могут сделать ранее полученные итераторы недействительными; после таких изменений обход следует организовать заново.

## 6. Правило пяти и управление ресурсами

В [Warehouse.h](../include/Warehouse.h) явно объявлены пять специальных методов. Их реализация находится в [Warehouse.cpp](../src/Warehouse.cpp).

1. **Копирующий конструктор `Warehouse(const Warehouse&)`.** Создаёт новый склад, копирует ограничение и число записей, вызывает `clone()` для каждого товара. Товары копии имеют отдельные адреса; изменение копии не меняет оригинал.
2. **Копирующее присваивание `operator=(const Warehouse&)`.** Работает с уже существующим получателем. Проверяет самоприсваивание, готовит временный вектор клонов, затем заменяет содержимое. Возвращает ссылку на получатель.
3. **Конструктор перемещения `Warehouse(Warehouse&&) noexcept`.** Передаёт ресурсы вектора без клонирования товаров, обнуляет счётчик источника и обновляет указатели владельца.
4. **Перемещающее присваивание `operator=(Warehouse&&) noexcept`.** Передаёт содержимое в уже существующий склад, освобождая его прежние товары; проверяет самоприсваивание и обновляет владельцев.
5. **Деструктор `~Warehouse()`.** Определён через `= default`. Вектор уничтожает находящиеся в нём `unique_ptr`, а они освобождают товары. Виртуальный деструктор `Product` обеспечивает полиморфное уничтожение.

`std::move` сам не выполняет перенос: он позволяет выбрать перемещающую операцию. `noexcept` — обещание не выпускать исключения; выход исключения из такой функции приводит к `std::terminate`.

Владение товарами выражено через RAII и `unique_ptr`. Возвращаемые поиском обычные указатели не владеют товарами. После удаления товара или уничтожения его владельца пользоваться такими указателями нельзя.

## 7. Результаты пяти демонстрационных сценариев

Демонстрационный режим `warehouse_demo --demo` завершился с кодом `0`. Без аргументов программа открывает интерактивное меню. Ниже приведены фактические значения запуска. Полный исходный вывод сохранён в [results/demo-output.txt](results/demo-output.txt). Имена типов и сообщения программы в протоколе оставлены без перевода, чтобы сохранить подлинный вывод; пояснения отчёта написаны на русском.

### Сценарий 1. Фабрики и обход склада

Создан склад вместимостью 6 записей. Через шесть фабрик добавлены и выведены итератором:

| Товар | ID | Цена | Остаток | Вес |
|---|---:|---:|---:|---:|
| Smartphone | 1 | 800 | 5 | 0.2 |
| Laptop | 2 | 1500 | 3 | 1.7 |
| TShirt | 3 | 40 | 10 | 0.3 |
| Jacket | 4 | 120 | 6 | 0.9 |
| Milk | 5 | 3 | 20 | 1.0 |
| Bread | 6 | 2 | 15 | 0.5 |

**Результат:** выведены все 6 товаров в порядке добавления. Общий интерфейс сохраняет конкретные типы товаров.

### Сценарий 2. Независимость глубокой копии

Скопирован склад с телефоном ID 10. В копии количество увеличено на 3, цена заменена на 750.

| Склад | Цена телефона | Остаток |
|---|---:|---:|
| Оригинал | 700 | 4 |
| Копия | 750 | 7 |

**Результат:** изменение копии не изменило исходные значения. В тестовой программе дополнительно проверяется различие адресов товаров оригинала и копии.

### Сценарий 3. Перемещение склада

Склад с одним ноутбуком передан новому объекту через конструктор перемещения. В демонстрации получены значения:

- размер источника после перемещения — `0`;
- размер получателя — `1`.

Одних размеров недостаточно для доказательства отсутствия копирования. Поэтому отдельно выполнена проверка адреса одного товара до и после move-конструктора и move-присваивания. Исходник этой дополнительной проверки: [results/check_move.cpp](results/check_move.cpp). Её [фактический вывод](results/move-output.txt):

```text
move_constructor_same_address=1
source_size_zero=1
move_assignment_same_address=1
moved_size_zero=1
```

**Результат:** для проверенного товара адрес сохранён в обеих операциях перемещения; отдельная копия товара не создавалась. Число проверенных товаров в дополнительном эксперименте — 1. Это подтверждение данного сценария, а не проверка всех возможных ошибок перемещения.

### Сценарий 4. Поиск и удаление

Добавлены телефон ID 30, ноутбук ID 31 и хлеб ID 32.

- По ID 31 найден `Laptop`.
- По категории `Electronics` найдено 2 товара.
- По цене 2 найден 1 товар.
- Удалён ноутбук по ID 31.
- Затем удалён первый оставшийся товар по индексу 0 — телефон.
- Итоговый размер склада — 1; остаётся хлеб.

**Результат:** три способа поиска и два способа удаления дали ожидаемые значения на выбранных данных.

### Сценарий 5. Перенос товара и изменение атрибутов

Молоко ID 40 перенесено из первого склада во второй через `transferTo`. После переноса количество уменьшено на 2, цена изменена с 3 на 4.

- Размер первого склада — 0.
- Во втором складе находится молоко ID 40.
- Цена молока — 4.
- Остаток — 8.
- Вес — 1.0.

**Результат:** товар оказался у другого владельца и сохранил возможность изменения атрибутов. Отдельный тест сравнивает адрес товара до и после переноса, подтверждая передачу того же объекта.

### Дополнительный консольный интерфейс

Интерактивное меню не требуется исходным условием лабораторной и добавлено для ручной работы с уже реализованными методами. При запуске без аргументов пользователь задаёт вместимость двух складов, выбирает активный склад, добавляет товары через фабрики, выполняет три поиска, два удаления, меняет цену и остаток, переносит товар другому владельцу и копирует активный склад во второй через оператор копирующего присваивания. Перед заменой товаров и вместимости запрашивается подтверждение. Вывод товаров использует собственный константный итератор. Данные сохраняются только до выхода из процесса.

Интерфейс реализован обычными функциями, `while`, `switch`, `std::getline`, `std::istringstream` и обработчиками исключений. Ссылки используются для передачи складов без копирования, указатель на активный склад позволяет переключать работу между двумя существующими объектами. Иерархия предметных классов не менялась; UML выше описывает именно её.

Числа разбираются целиком: ввод вроде `1junk` отклоняется. Отрицательные цены и остатки, неконечный вес и пустые названия не принимаются. В интерфейсе перед `changeQuantity` проверяется диапазон результата, а ID ограничивается значениями от 1 до `INT_MAX - 1`, чтобы не вызвать известные переполнения классов. Эти ограничения находятся в консольном слое и не исправляют прямые вызовы соответствующих методов извне.

[Протокол проверок меню](results/console-output.txt) включает 16 случаев: выход, полный цикл работы с товаром, ошибочный ввод, заполнение склада, дубли ID и поиск, границы остатка, полный склад-получатель, дубли ID у получателя, окончание ввода при запуске и добавлении, выбор всех шести фабрик, справку и неизвестный аргумент командной строки, подтверждение и отмену копирования, окончание ввода при подтверждении. Проверка копирования изменяет цену в копии и проверяет сохранение исходной цены. Тесты запускают настоящий исполняемый файл с подготовленным вводом; тайм-аут защищает от зависания при окончании ввода.

В живом терминале дополнительно проверены создание молока, просмотр, перенос во второй склад, переключение активного склада и завершение работы.

## 9. Известные ограничения реализации

Успешные сценарии не закрывают все граничные случаи. Ранее выявлены и остаются в текущем коде следующие проблемы:

- Неявное присваивание отдельного `Product` копирует невладеющий указатель на склад и ID; это может нарушить связь товара с владельцем. Правило пяти склада не исправляет присваивание отдельного товара.
- `Quantity::change` может переполнить `int` до проверки результата сеттером.
- Счётчик ID может переполниться на границе `int`.
- Проверка веса только сравнением с нулём пропускает `NaN` и положительную бесконечность.
- При переносе товар извлекается из источника до добавления в приёмник. Если выделение памяти в приёмнике не удастся, товар может быть потерян. Этот случай установлен чтением реализации; отказ памяти не инъецировался.

Глобальная уникальность явно переданных ID между разными складами не обеспечивается; копирование склада намеренно сохраняет ID его записей. Категории сравниваются с учётом регистра. Многопоточность не реализована и не проверялась.

Логирование — дополнительная часть проекта, не самостоятельный критерий предоставленного задания. `LoggingProxy` здесь используется как статический журнал операций, а не как реализация структурного паттерна «Заместитель».

## 10. Выводы

Реализована модель склада с тремя категориями и шестью конкретными товарами. Отдельные классы атрибутов скрывают значения и проверяют отрицательные числа. Фабрики создают товары через общий интерфейс, собственные итераторы предоставляют изменяемый и константный обход. Склад глубоко копирует товары через `clone` и передаёт владение через операции перемещения.

Пять демонстрационных сценариев дали ожидаемые результаты; прошли 10 тестовых функций и 4 проверки CTest, включая 16 проверок консольного интерфейса. Дополнительная проверка одного товара подтвердила сохранение адреса при move-конструкторе и move-присваивании. Практическая работа показывает различие между копированием данных, передачей владения и невладеющим доступом по указателю или ссылке.

Следующее улучшение — исправление перечисленных граничных ошибок и добавление соответствующих регрессионных проверок. Без этого утверждать полную корректность программы во всех случаях нельзя.

Конструктор вместимости принимает `int`, отклоняет значения `<= 0` и только после проверки преобразует число в `std::size_t` для хранения. Это исключает принятие отрицательного аргумента как огромного беззнакового числа. Проверены -1, -100, минимальное значение int и ноль.
